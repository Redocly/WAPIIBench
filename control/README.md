# `control/` — the raw-OpenAPI CONTROL condition

The control arm for the blinded agent-as-generator estimate in `estimate/`. Same model, same
68 tasks, same five candidate operations per task — the **only** intended difference is what
the model is given to write the call against:

| | treatment (`estimate/`) | control (`control/`) |
|---|---|---|
| API given as | a generated typed TypeScript client, filtered to 5 operations | the **OpenAPI description** of the same 5 operations |
| answer | a call through the client, `{index}_code.ts` | a plain `fetch(...)` call, `{index}_code.js` |

**Why it exists.** The treatment's number on its own says nothing about the typed SDK: a
model handed five candidate operations and a task might do just as well reading the
description text. The control isolates the SDK's contribution by holding everything else
fixed — the same sample (`estimate/sample_parseable.json`), the same per-task five-operation
whitelists (`estimate/whitelists_parseable.json`, **reused**, not re-retrieved), the same
capture shim, the same `evaluation.compare()` / `evaluation.analyze()`, the same statistics
functions imported from `estimate/score_driver.py`. The difference between the two arms'
correctness rates is the estimate of what the generated client buys, subject to the
asymmetries listed at the bottom — the first of which is large.

Nothing in here modifies the arm or the treatment. `wapiibench/capture_shim.js` is reused
byte-for-byte; `wapiibench/sdk_repair_arm.py` and `wapiibench/evaluation.py` are imported,
never edited; `estimate/` is read-only from here.

Protocol and the ready-to-use prompt: **`control/RUNNER_CONTRACT.md`**.

## Order of operations

```
python control/build_specs.py                    # work/{api}/{index:04d}_spec/ + spec_sizes.json
python control/check_auth_parity.py              # auth_parity.json  (needs estimate/work/ clients)
python control/build_manifest_control.py         # prompts/{api}/{index}_prompt.md + task_manifest_control.json
python control/token_sizes.py                    # token_sizes.json
python control/blinding_check_control.py         # blinding_report_control.json (fails on a hard leak)
python control/verify_manifest_control.py        # manifest_verification_control.json
python control/verify_control.py                 # verification.json (plumbing, no model)

# -> dispatch one FRESH agent per task_manifest_control.json row; it writes answer_path

python control/score_driver_control.py --population 228     # results/verdicts.json
```

`control/work/` must be deleted before a rebuild, not rebuilt over, for the reason
`estimate/README.md` gives: a spec directory written before the parameter-type table existed
has no `wapii_param_types.json`, and the capture shim then silently leaves every query value
a string.

## The two deliberate differences in the execute stage

`control/execute_fetch.py` replaces `evaluation.execute()` (whose `.js` branch matches
`axios\.[a-z]+\(` and would score every plain-`fetch` answer `ABSENT_REQUEST` without running
it) and `sdk_repair_arm.execute_sdk_repair()` (which compiles TypeScript against a generated
client that does not exist here). Its docstring cites this file for two departures from
`execute_sdk_repair()`, so here they are in full:

**A. The answer is wrapped in an async IIFE — a small advantage to the control.**
Node runs stdin as CommonJS, where top-level `await` is a `SyntaxError`. A perfectly correct
request written as `await fetch(...)` would then score `nonexecutable` for a harness detail
that has nothing to do with the model. The treatment is not exposed to this: `tsc` catches a
TS candidate's top-level await and the treatment has up to 3 repair rounds to fix it, which
the control does not have. Wrapping is semantically inert for code that does not use
top-level await, and the shim writes the config synchronously inside the `fetch` call, so
nothing depends on the promise being awaited. Net effect: the control is protected from one
failure mode the treatment repairs its way out of. Disclosed as an advantage to the control.

**B. A run that produces no config file is recorded as `EXECUTION_ERROR`, even when node
exits 0 — stricter on the control than the treatment's rule is on the treatment.**
`execute_sdk_repair()` writes the error file only when the exit code is non-zero, so an
answer that runs cleanly without issuing a request leaves no `{index}_config.json`,
`compare()` never sees the task, and it silently drops out of the denominator. An answer with
no request is a wrong answer, not an absent one, so the control counts it. Each row of the
driver's output carries `request_captured` and the summary reports `no_request_captured`.

## Population: score both arms at N = 228

`control/score_driver_control.py` defaults to `--population 228`, the parseable-API frame both
arms are drawn over (`task_manifest_control.json` records `frame = "parseable-apis-only"`,
n = 68; the frame itself is justified in `estimate/README.md`, "Why the population changed").

**`estimate/score_driver.py` still defaults to N = 395**, kept for continuity with numbers
already recorded under it. The treatment must therefore be re-run as
`python estimate/score_driver.py --population 228` before the two confidence intervals are
put side by side; the control's driver prints that command line at the end of every run.
Comparing a 228-corrected control interval against a 395-corrected treatment interval is an
error, and it is an easy one to make.

Neither arm supports per-API claims: `google_sheet_v4` contributes 5 draws and
`google_calendar_v3` 11.

## Asymmetries a reviewer could attack

Ordered by how much they could move the result. Every one is a real difference between the
conditions beyond "typed client vs. description text".

1. **NO REPAIR LOOP IN THE CONTROL; THE TREATMENT GETS THREE `tsc` ROUNDS.** The largest
   asymmetry in the design and the one to lead with. A plain `fetch` call is untyped, so
   there is nothing to type-check and no error signal to repair against, while the treatment
   may edit its file up to `sdk_repair_arm.DEFAULT_MAX_RETRIES` = 3 times against real
   compiler output. Part of any measured gap is *the existence of a checker*, not the typed
   client's help in writing the call. This design cannot separate the two, so the gap is an
   upper bound on "the typed client helps" and must never be reported as
   "typed SDK vs. OpenAPI description" without the words "with a compile-repair loop vs.
   without one". (`RUNNER_CONTRACT.md` section 2.)
2. **The treatment's starter also registers `zodValidation()`** — a second, runtime checker
   the control has no counterpart for. Same direction as (1).
3. **`Authorization` is easier for the control.** Every expected config carries
   `Authorization: Bearer <token>`, and `Authorization` is not in `evaluation.SPECIAL_KEYS`,
   so a captured request without it scores `MISSING_KEY`. The control writes its own headers
   and the starter hands it the constant; the treatment depends on the typed client's
   `auth()` mechanism, which the treatment's own deviation 8 records as producing captured
   requests without the header. This favours the **control** on the headline number, which is
   why both arms report `DIAGNOSTIC_correctness_ignoring_auth_header` beside it.
4. **`components` pruning favours the control.** `build_specs.py` prunes the control's
   document to the transitive `$ref` closure of the five surviving operations; `filter-in`
   prunes operations only, so the treatment's `client.ts` still carries the API's whole type
   surface. `spec_sizes.json` records both the pruned and the unpruned size (median 26.8 kB
   pruned vs 72.5 kB unpruned) so the confound can be read in either direction. The choice
   was made deliberately towards a **stronger** control, because a weakened control inflates
   the SDK's apparent contribution.
5. **The artifact the treatment must read is 1.2–10.6x larger** (median 3.86x in pretokens,
   larger on 68/68 tasks). That cuts against the treatment — more context to work through —
   and it also means "the typed SDK is the token-efficient way to describe an API" is not
   supported on this population. Pretokens, not BPE tokens: no tokenizer vocabulary was
   reachable from this container.
6. **Starter provenance differs.** The treatment's starter is `evaluation.SETUPS`
   `['sdk-invocation']`, read live out of `evaluation.py` through the AST; the control's is
   defined in `control/fetch_starter.py`, because no fetch-shaped `SETUPS` entry exists and
   `evaluation.py` belongs to the arm. The content mirrors the treatment's line for line, but
   one side's starter is the harness's and the other's is the control's.
7. **The auth line is derived from different sources**: the generated client's
   `OPERATIONS[...].security` in the treatment, the spec's `security` / `securitySchemes` in
   the control. Checked rather than argued — 68/68 agreement, 0 disagreements
   (`auth_parity.json`) — but it is two rules, not one.
8. **The capture seam differs.** The treatment injects the shim's capture function as the
   generated client's `fetch` option; the control assigns it to `globalThis.fetch`
   (`capture_global_fetch.js`, one line — measured necessary: with the shim alone a
   hand-written `fetch` runs, exits 0 and captures nothing). Everything after the seam —
   normalization, spec-declared coercion, the config shape, the synthetic 200 — is the
   treatment's unmodified code.
9. **The prompts are not word-for-word parallel.** The control's rules add clauses the
   treatment's do not have (where query vs. body vs. path parameters go; do not wrap the call
   in a function), and drop the whole `tsc` paragraph. Extra instruction could help the
   control or distract it; either way the two prompts are not identical outside the
   substituted material.
10. **One blinding finding stands on the control and none on the treatment.** The control's
    manifest verification reports `clean = false` on a single `ground_truth_asymmetric`
    finding: slack #27's filtered spec names `admin_inviteRequests_approve` four times and
    the other four ids once each, because the source spec has `admin_inviteRequests_deny`
    `$ref` the shared component
    `#/components/requestBodies/admin_inviteRequests_approve` — OpenAPI names a shared
    component after whichever operation defined it, and `generate-client` never exposes this
    because it writes each operation into `client.ts` once. The aggregate settles it: only 2
    of 68 tasks have a unique maximum at all, and on both the winner is that same id — a
    distractor on slack #0, the ground truth on slack #27. The count tracks which operation
    owns a shared component, not which one is the answer. Removing it entirely would mean
    renaming or inlining shared components in `build_specs.py`.
11. **Ordering exposure, measured on both sides.** Ground truth is first among the five in the
    control's emitted spec order on 14/68 tasks (20.6% vs a 20% baseline), and the emitted
    order is spec order on 68/68 with 0 file orders unexplained by sorted-or-spec order (the
    treatment had 6, from `generate-client`'s own `OPERATIONS` grouping). Not an asymmetry
    against the control, but a reviewer will ask, so the numbers are recorded.
12. **A residual advantage shared by both arms, so it does not bias the contrast but does
    bias the absolute rates:** the five-operation whitelist is guaranteed to contain the
    ground-truth operation, making endpoint choice 1-of-5 rather than 1-of-N, and on the one
    task where the stand-in retriever missed it (slack #52) it was substituted in. Because
    the control **reuses** the treatment's whitelists, this error is identical in the two
    arms rather than independently drawn — which is what makes a task-by-task comparison
    legitimate, and also means neither arm's absolute rate is a WAPIIBench rate.
13. **Pre-flight evidence differs in kind.** The treatment has `dryrun/` (three hand-written
    placeholder artifacts); the control has `verification.json` (shim/coercion plumbing, 4
    derived cases) and `score_driver_smoke.json` (2 answers end to end). Neither is a
    measurement, and they are not the same check.
