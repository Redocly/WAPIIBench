# `estimate/` — blinded agent-as-generator estimate of the typed-SDK arm

Scaffolding for a rough, blinded correctness estimate of the `sdk-repair` arm using a Claude
subagent as the code generator, so the arm's correctness can be bounded before a GPU is
booked for open-weight models.

**Nothing in here modifies the arm.** `wapiibench/sdk_repair_arm.py`,
`wapiibench/capture_shim.js` and `wapiibench/evaluation.py` are read-only from this
directory: they are imported (`harness_import.py`, `build_clients.py`, `score_driver.py`) or
read as text (`emit_prompt.harness_starter()` parses `evaluation.py`'s AST for the starter, so
it can never go stale against a concurrently edited file).

## Population and sample size

### Why the population changed (2026-09-02) — read this before quoting any number

The original frame (`sampling_frame.py`) drew 78 tasks from all **N = 395** synthetic tasks.
That frame is superseded, and `sample.json` is kept only for the record.

Scoring a task requires `evaluation.compare()`, which calls
`openapi_utils.parse_spec(openapi/real_world_specs/{api}.yaml)` (`evaluation.py:551`) and
resolves the expected URL against the fully-parsed `openapi_parser.Specification`. **A spec
that does not parse makes every task on that API unscoreable**, however good the generated
answer is. The arm's *generation* path never notices, because it reads specs with
`yaml.safe_load` — so the failure is invisible until scoring time and then costs the whole
stratum. Measured with the harness's own parser (`estimate/check_parse_support.py` ->
`parse_support.json`):

| API | `parse_spec` |
|---|---|
| `slack` | parses |
| `google_calendar_v3` | parses |
| `google_sheet_v4` | parses |
| `asana` | **never completes** within the run budget |
| `github_v3` | **ParserError** |
| `npm_registry` | **ParserError** |

`asana` alone is 167 of the 395 synthetic tasks and was 33 of the original 78-task sample.
Keeping the old frame and simply discarding the unscoreable draws would leave ~45 scored
tasks, whose 95% half-width at p = 0.5 is about **+/-15pp** with the FPC — the estimate
would no longer answer the question it was sized to answer. So the sample was **redrawn**
over the parseable strata (`sampling_frame_parseable.py`).

**What that costs.** The population is now narrower: this estimate covers the arm's
correctness rate on the three parseable synthetic APIs, **not** all 395 synthetic tasks and
certainly not WAPIIBench as a whole. Report it that way.

### The arithmetic

Target +/-10 percentage points, 95% confidence, worst case p = 0.5, on
N = 174 + 37 + 17 = **228**:

```
n0 = z^2 p(1-p) / e^2 = 1.959964^2 * 0.25 / 0.10^2 = 96.036472
n  = n0 / (1 + (n0-1)/N) = 96.036472 / (1 + 95.036472/228)
                         = 96.036472 / 1.41682663 = 67.782797
n  = 68                                     (ceil)
```

Proportional allocation, largest-remainder rounding:

| stratum | size | exact | allocated |
|---|---|---|---|
| `slack` | 174 | 51.894737 | **52** (largest remainder) |
| `google_calendar_v3` | 37 | 11.035088 | **11** |
| `google_sheet_v4` | 17 | 5.070175 | **5** |
| | 228 | 68.000000 | **68** |

Seed `20260902`, recorded in `sample_parseable.json` and `sample_meta_parseable.json`;
re-running the frame reproduces the identical 68 ids (verified).

### NO PER-API CLAIMS ARE SUPPORTABLE

The +/-10pp buys a half-width of ten points on the **overall** rate across these three APIs
and nothing else. `google_sheet_v4` contributes **5** draws and `google_calendar_v3`
**eleven**; a proportion from 5 observations has a 95% half-width near +/-40pp. Do not
table, quote or infer a per-API rate from this sample — `sample_meta_parseable.json` carries
`"supports_per_api_claims": false` for exactly this reason. `score_driver.py`'s FPC also has
to be run with `--population 228`, not the default 395.

## Order of operations

```
export REDOCLY_TELEMETRY=off                            # NOT optional: ~0.8 s vs minutes per client

python estimate/check_parse_support.py                  # parse_support.json (which APIs can be scored)
python estimate/sampling_frame_parseable.py             # sample_parseable.json, sample_meta_parseable.json
python estimate/retrieval_standin.py     --sample estimate/sample_parseable.json     --out estimate/whitelists_parseable.json            # whitelists (+ retrieval accuracy)
python estimate/build_clients.py     --whitelists estimate/whitelists_parseable.json     # work/{api}/{index:04d}_client/
python estimate/blinding_check.py     --sample estimate/sample_parseable.json     --out estimate/blinding_report_parseable.json       # fails on a hard leak
python estimate/build_manifest.py                       # prompts/{api}/{index}_prompt.md + task_manifest.json
python estimate/verify_manifest.py                      # manifest_verification.json (fails on any finding)

# -> dispatch one FRESH agent per task_manifest.json row; it writes answer_path

python estimate/score_driver.py --population 228        # results/verdicts.json
```

`estimate/work/` must be deleted before a rebuild, not rebuilt over: a client generated
before the parameter-type table existed has no `wapii_param_types.json`, and the capture
shim then silently leaves every query value a string (see deviation 6).

## Declared deviations

1. **Retriever.** The paper's `rag.retriever` needs `all-MiniLM-L6-v2` plus a
   `sentence_transformers` CrossEncoder from huggingface.co, which network policy blocks here.
   `retrieval_standin.py` is a pure-Python BM25 over each operation's path, method,
   operationId, tags, summary, description, parameter names and request-body property names.
   Measured on the operative 68-task sample: **top-1 0.838, top-5 0.985** against the
   paper's reported 0.757 / 0.952 (it was 0.795 / 0.987 on the superseded 78-task sample). Do not read that as "as good as the paper's retriever" — see the report's
   threats section; these tasks were generated from these specs, so lexical overlap is
   inflated.
2. **Whitelist width 5, ground truth guaranteed.** One task per operation in this dataset
   means a one-operation client would give endpoint choice away. Five matches `num_chunks=5`.
   The ground-truth operation is always in the whitelist; on the **1 of 68** tasks where the
   stand-in missed it (`slack` #52, ground truth `admin_users_setAdmin` at retriever rank 6)
   it was substituted in and the 4 top distractors kept. Recorded per task in
   `whitelists_parseable.json`. Ground truth resolved for all 68 tasks (0 unresolved).
3. **`matchStrategy`.** `sdk_repair_arm.filter_spec()` hardcodes `matchStrategy: "all"`,
   which is satisfiable only for a one-element whitelist; with five operationIds
   `generate-client` silently emits `OPERATIONS = {}`. `build_clients._patch_match_strategy`
   rewrites that one key to `"any"` in the config `filter_spec()` just wrote. The arm needs
   the same one-word fix.
4. **Absolute `code_dir`.** `sdk_repair_arm._compile_to_js` runs `npx tsc <ts_file>` with
   `cwd` set to the client dir, so a relative path fails with TS6053 and every task scores
   EXECUTION_ERROR. `score_driver.py` always passes an absolute path.
5. **Prompt emitter renders `{auth_setup}`.** `evaluation.SETUPS['sdk-invocation']`
   gained an `{auth_setup}` line in the arm's coercion commit, and
   `sdk_repair_arm.assemble_prompt()` substitutes it (line 798) with
   `auth_setup_for(client_dir)` before a model ever sees the starter.
   `emit_prompt.harness_starter()` reads the starter as raw text, so it was handing the
   generator a **literal `{auth_setup}` line** — not valid TypeScript, so `tsc` would
   reject every artifact on round 1 and the agent would either burn repair budget on it or
   delete it, dropping the `Authorization` header every expected config in this dataset
   requires. `emit_prompt._auth_setup()` now performs the same substitution the arm
   performs. Still blinded: `auth_setup_for()` derives the line from the generated client's
   own `OPERATIONS[...].security` entry, i.e. from the API description, never from a task
   or an expected config.

6. **Parameter-type table in the estimate path.** `build_clients.py` did not call
   `sdk_repair_arm.write_param_types()`, so its clients carried no `wapii_param_types.json`
   and `capture_shim.js` coerced nothing: a captured `limit` came back as `"100"` while the
   benchmark expects `100`, and the task scored `wrong`. (The arm's execute-time fallback
   cannot cover this — it needs `task["api"]`, and the per-API synthetic task dicts only
   have `task` and `config`.) `build_clients.py` now calls it, wired exactly as
   `sdk_repair_verify.build_case_dir()` does: the spec and the operationId whitelist are the
   only inputs. Verified end to end on a slack query integer and a google_sheet_v4 query
   boolean — both `correct` with the table, both `wrong` without it.

7. **`redocly.yaml`'s whitelist order was a blinding hole.** `filter_spec()` writes the
   five operationIds into `decorators.filter-in.value` in **retriever-rank order**, and that
   config file lands inside the client directory the agent is told to read. The ranking puts
   the ground truth first on ~84% of tasks and, on a substituted task, first by
   construction. `build_clients._patch_match_strategy` now also `sorted()`s that list;
   `matchStrategy: "any"` is order-independent, and the generated `client.ts` is
   byte-identical before and after (verified on all 68). Measured after the fix: the ground
   truth is first in the order a reader of `client.ts` meets the five ids on **15 of 68**
   tasks (22.1%), against the 20% chance baseline.

8. **`Authorization`.** Every expected config carries `Authorization: Bearer <token>` and
   `Authorization` is not in `evaluation.SPECIAL_KEYS`, so a captured request without it
   scores `MISSING_KEY` and the task comes out `wrong`. The typed client only sends it if
   something calls `client.auth.bearer(...)`, and the current `sdk-invocation` starter does
   not. `score_driver.py` reports the harness verdict as the headline and a separate
   `DIAGNOSTIC_correctness_ignoring_auth_header`. The real fix belongs in the arm.
